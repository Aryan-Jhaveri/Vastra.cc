# Contributing

Thanks for helping. This page covers setup, tests, conventions and how a pull
request makes its way into Vastra.

## Setup

```bash
git clone https://github.com/Aryan-Jhaveri/Vastra.cc.git vastra
cd vastra
npm install
(cd src/transport/web/app && npm install)
cp .env.example .env          # the mocks are on by default; add GEMINI_API_KEY for real AI
bash scripts/setup-hooks.sh   # installs the commit-msg hook
npm run web:dev               # API on :3000, Vite on :5173
```

Without a mail provider configured, sign-in links are printed in the server log.
See [README.md](README.md) for the AI key layers and [DEPLOY.md](DEPLOY.md) for
running with your own model servers.

## Tests

Every change comes with tests, and a pull request must pass all of these:

```bash
make test-selfhost   # backend (vitest): test/**
make web-test        # frontend (vitest + jsdom): src/transport/web/app/test/**
make web-tsc         # frontend typecheck with no cache
npx tsc --noEmit -p . # backend typecheck
```

`make web-tsc` runs `tsc -b --force` in `src/transport/web/app`. The frontend
has its own, stricter `tsconfig`, and an incremental cache can hide errors, so
always run it clean before pushing frontend changes. `make smoke-selfhost` boots
the server with no keys and checks it answers; `make migrate-fresh` applies every
migration to an empty database.

Conventions:

- Backend tests live in `test/**`, mirroring `src/`. Colocated
  `src/**/*.test.ts` files are not picked up.
- Frontend tests live in `src/transport/web/app/test/**`.
- **Every data query takes a `userId`.** Never make it optional or default it.
  Validate it at runtime with `requireUserId()` from `src/db/queries.ts`.
- **Test cross-user isolation.** A new query or route needs a test showing one
  user can't read or change another user's data. Foreign ids return "not found".
- Images are read and written only through `src/storage/images.ts`.
- AI calls go through `generateText` / `generateJSON` in `src/ai/client.ts` and
  are recorded by `runInstrumented` in `src/ai/instrumented.ts`; don't call a
  provider SDK directly.

## Database changes

If you change `src/db/schema.ts`, generate a migration and commit it:

```bash
npm run db:generate
```

Migrations apply automatically when the server starts. Don't edit an existing
migration.

## Dependencies

- No floating versions (`"latest"`, `"*"`, `"x"`, `""`) in any `package.json`;
  `test/packageManifest.test.ts` fails the build if one appears.
- Upgrade a major version in its own pull request, with the full test suite run
  and the reason in the description. Never as a side effect of `npm audit fix`.

## Commits and pull requests

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/),
and the `commit-msg` hook enforces it:

```
type(scope): short description

Optional body explaining why, not what.
```

Types: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `style`, `perf`,
`ci`, `revert`.

Keep pull requests focused: one change, with its tests. The template asks for a
summary, the linked issue and test status.

## How your change reaches Vastra

This repository is exported from the main Vastra codebase. Pull requests here
are reviewed and then imported upstream, and they come back in the next export.

Some files are generated by the export and must not be edited in a pull request
(changes to them can't be imported):

- `src/hosted/index.ts` and `src/transport/web/app/src/hosted/index.tsx`
  (stubs for features that only exist on vastra.cc)
- `README.md`, `CONTRIBUTING.md`, `DEPLOY.md`
- `.env.example`

If one of these needs a change, open an issue instead.

## What not to include

- Secrets or `.env` values
- `node_modules/` or build output
- AI-assistant attribution lines in commit messages
